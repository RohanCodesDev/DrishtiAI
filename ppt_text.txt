0. The One Rule Before You Build This
Faculty review is lower-stakes than the SIH finale, but it's also where a habit gets set. Every claim on your slides should be one of two colours: green — you can demo it live right now, or amber — this is where the architecture is going and why. Never present a target feature as a completed one. This document tags every bullet below so you can copy them straight in without guessing which bucket they belong to.
This isn't just about avoiding an awkward question — it's a stronger pitch. "We know exactly what we're building and can explain every design decision" reads as more credible to faculty than a wall of impressive-sounding numbers no one can verify on the spot.

1. Slide-by-Slide Content Plan

Slide 1 — Title & Problem Framing
Headline: DRISHTI — Privacy-Preserving Visual Intelligence for Browser Agents
Subhead: On-device perception, local privacy firewall, validated cloud reasoning
PS 26171 • ISRO, Dept. of Space • Theme: Smart Automation
One line naming the gap: today's browser agents send raw screens/DOM to the cloud — passwords, faces, IDs and all
One line naming your fix: a local privacy firewall between the screen and the cloud, so only sanitized context is ever transmitted

Keep this slide almost entirely text-free beyond the headline — let the tagline and problem/gap framing carry it. Save visuals for Slide 6.

Slide 2 — Proposed Solution & Approach
 [BUILT NOW] 11-Rule Privacy Firewall: On-device redaction of Emails, Phones, IDs, and API keys before they leave the browser
 [BUILT NOW] Local Visual Perception: Offscreen WASM Tesseract.js OCR and Hardware FaceDetector API for human face blackout shielding
 [BUILT NOW] Server-side VLM/LLM reasoning that receives strictly sanitized DOM context and returns a strict action schema
 [BUILT NOW] Interactive "Click-to-Inspect" Web Lens with live decoding and Human-in-the-Loop Action Validation
 [TARGET / ROADMAP] Autonomous Multi-Tab Web Research & Synthesis Engine for cross-referencing information
 [TARGET / ROADMAP] ONNX Runtime Web Local Named Entity Recognition (In-browser MiniLM) for offline contextual parsing
This is the slide most likely to draw follow-up questions — be ready to point at your live redaction and OCR demo as your proof of concept.

Slide 3 — Feasibility & Current Status
Show your actual roadmap, not invented benchmarks. A simple checklist reads as more credible than unverifiable millisecond figures:
 [BUILT NOW] Phase 0-4: extension scaffold, popup UI, DOM/page structural understanding — done
 [BUILT NOW] Phase 5-9: PII Privacy Firewall, backend API, LLM reasoning, safe auto-loop actions — done
 [BUILT NOW] Phase 10-14: Dual-mode WASM OCR, Native Face Redaction, Web Lens UI, and Zero-Leak Audit Certificates — done
 [TARGET / ROADMAP] Phase 12-13: Multi-Tab orchestration and ONNX Runtime Web NER — in progress, current focus
 [TARGET / ROADMAP] Phase 15: Final Showcase Polish and benchmarking — planned
If you have any real number — e.g. actual DOM-extraction time on your own laptop (e.g. 2ms DOM, 185ms WASM OCR), use that instead of an invented one. A small honest number beats a large invented one.

Slide 4 — Impact & Use Cases
Keep 3-4 sectors, one line each, and stay descriptive rather than quantified until you have real evidence:
BFSI: agent-assisted form filling and statement review without card numbers or IDs ever leaving the device
Healthcare / EHR: assistants that can navigate patient portals without transmitting identifiable medical data
Government / DPI: citizen-facing portal assistance (DigiLocker-style flows) with identity fields shielded locally
Enterprise dashboards: automation on internal tools without screen data leaving the corporate network
Avoid citing specific laws (DPDP Act, HIPAA, GDPR) as "compliant with" unless you can defend that claim — safer framing is "designed in the spirit of privacy-by-design principles like GDPR Article 25."

Slide 5 — Research & Prior Art
Ground the idea in real, checkable references — this signals you did the reading:
WebVoyager (He et al., 2024) — reference multimodal browser agent architecture (screenshot + Set-of-Mark + ReAct loop)
OmniParser (Microsoft) — vision-based screen parsing into structured UI elements, closest analogue to your local perception layer
Microsoft Presidio — open-source PII de-identification framework; the right reference for your recognizer taxonomy and precision/recall methodology
ONNX Runtime Web + WebGPU (Microsoft) — the standard path for client-side model inference in-browser, explicitly named in the PS
Drop unverifiable citations like a specific "Kovac et al." skin-chromaticity paper or an ECMAScript section number unless you've actually read and can discuss them — faculty are more likely than SIH judges to ask a follow-up on a named citation.

Slide 6 — Architecture & Roadmap
Two diagrams side by side works well here: 
Left: your current built architecture (Phases 0-11 & 14) running today
Right: the target end-to-end architecture (incorporating Multi-Tab & ONNX)
Close with a simple roadmap strip emphasizing what is built vs what's next.

2. Design Recommendations

2.1 Visual language
Your own template's instinct — a clean aerospace/mission-control look — fits the ISRO problem statement well and reads as more mature than a generic tech-startup deck. Keep it restrained:

Element | Recommendation
Background | Deep navy (#0E1526) or off-white (#F7F9FB) — pick one and use it for every slide, no mixing
Accent colour | One accent only: cyan/teal (#0E7C86) for "safe/protected", amber (#C9821E) reserved only for risk/attention states
Danger colour | Muted red (#AE3B3B) used sparingly — only for the "raw/leaked" side of any before-after comparison
Typography | One clean sans-serif throughout (Inter, Calibri, or Segoe UI) — bold weight for headlines, regular for body, never more than 2 sizes per slide
Icons | Simple line icons (shield, eye, lock, checkmark) — avoid clip-art or emoji on the actual slides, even though they're fine in your working docs
Data viz | Simple bar/checklist visuals showcasing your 0-leak certificates and latency (e.g. 185ms OCR)

2.2 Layout rules
One idea per slide — if Slide 2 is fighting for space between architecture and features, split the feature list into speaker notes and keep only 4-5 bullets visible
Consistent header position and accent bar on every slide — reinforces that this is one coherent system, not six unrelated slides
Never run text edge-to-edge — keep a consistent margin (roughly 6-8% of slide width) so nothing looks cramped on a projector
Use the BUILT/TARGET colour convention from Section 1 directly on the slide too, not just in this planning doc — a small green/amber tag next to each bullet is an honest, memorable device that faculty will notice positively

2.3 The one visual worth investing time in
A simple before/after panel: left panel shows a raw dashboard screenshot with a face, email and phone number visible in red boxes; right panel shows the same screenshot with those fields replaced by <PERSON_1>, <EMAIL_1>, and a 👤 [FACE REDACTED] shield in a clean sanitized style. This single image does more work than any bullet list — it's the entire pitch in one glance. You should use a real screenshot of your extension's Phase 5/6/10 outputs for this.
